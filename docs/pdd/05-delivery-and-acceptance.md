# 拼多多模块实施计划与验收

版本：0.1，2026-10-13。关联：[产品方案](07-product-proposal.md)、[接入架构](02-integration-and-sync.md)。状态：开发规划，尚未执行开发或真实接入。

## 1. 交付安排与估算

默认一名熟悉现有工程的全栈开发，运营负责人参与接口核验及业务验收。以下为有效开发工作日粗估，非交付承诺；不含应用审批等待、资质补办、图片/商品资料整理及外部平台故障。

| 阶段 | 工作包 | 估算 | 交付门槛 |
| --- | --- | --- | --- |
| A 接入验证 | 应用申请指导、官方契约/模板样例、单店授权与只读接口小样 | 4–6天 | 读取/发布能力矩阵实测，不支持的能力有明确路径 |
| B 接入底座 | 店铺绑定、凭据、权限范围、队列/租约、任务页 | 6–9天 | 两店隔离、授权撤销、重启恢复验证 |
| C 同步闭环 | 订单/售后/商品、游标/分页、回补、导入预览与去重 | 8–12天 | 两店最近7天核对，重复任务不重复事实 |
| D 汇总与映射 | 指标字典、质量、SKU映射、趋势/排名/导出 | 5–8天 | 跨期/部分退款/未映射示例正确，缺口可解释 |
| E 发布闭环 | 单店草稿、类目/属性/素材、预检、冻结、提交/审核/unknown核实 | 8–12天 | 单店单商品真实结果核验，失败不重复创建 |
| F 多店与试运行 | 多店差异预览、分店提交、权限/故障回归、监控、发布演练 | 5–8天 | 两店发布或按权限明确人工路径，小范围试运行通过 |
| 合计 | 逐步交付 | 36–55天 | 每阶段可单独演示，核心接口能力变化后重估 |

审批与开发可以部分重叠；使用替身阶段不算官方实测完成。读取能力获批而发布未获批时，优先交付数据中心与资料包，将自动发布标为待开通；不让整个数据模块无限等待发布权限。

## 3. 发布前必须核实的外部条件

- 应用是否允许自有多店/这些店铺授权，读取和发布能力是否真正获批。
- 官方授权/续期、签名、网关、返回码、限流和历史窗口规则。
- 完整退款事件是否可获得；不能获得时哪些指标须降级。
- 商品创建后能否按请求关联核实；不能核实时人工处理路径是否可接受。
- 发布类目、品牌/资质、规格、图片、运费模板及价格规则。
- 允许的测试方式。若无沙箱，以明确授权的测试店、测试商品执行一次真实发布，不能用prod访问官方实店却标为Mock。

尚未满足的项标 pending、列负责人和下一步。官方发布权限是自动上架功能的依赖；不影响可在替身下完成框架与可读数据产品的内部验证。

## 4. 测试环境

复用项目 local/test/prod 隔离，集成测试仅使用显式本地库名以 _test 结尾的数据库，例如 bebefish_pdd_test。不能借用开发经营数据库或覆盖现有数据。生产不可启用Mock授权、远程响应替身或默认管理员。

后端沿用 Java 21/Maven/MySQL 8。前端沿用 Vitest，执行 npm run test:run；构建设 VITE_RUNTIME_ENV=test、VITE_DATA_SOURCE=real 后 npm run build。本文件不提供真实密钥。网络依赖测试与默认测试套件分开，默认套件不发布真实商品。

后端测试包括业务单元、适配器契约替身、真实MySQL事务/并发测试；前端覆盖状态、版本竞争、权限与输入保留；浏览器验收验证完整操作链。已存在全量测试也需在最终实现完成后回归，不能以现有906项通过证明新模块正确。

## 5. 验收矩阵

| 编号 | 情景 | 必须结果 |
| --- | --- | --- |
| AUTH-01 | A/B店重名或同外部单号 | 身份依外部ID，不串店 |
| AUTH-02 | 授权到了错误店铺 | 不覆盖原授权，候选token不能供任务调用 |
| AUTH-03 | state过期/重放、刷新与重新授权竞争 | 拒绝过期/重复，旧generation不能覆盖新凭据 |
| ACL-01 | A店人员请求B店详情/汇总/任务/导出 | 后台拒绝，不能泄露B店数量 |
| ACL-02 | 排队后撤销人员权限或停用店铺 | 新副作用暂停，下载拒绝，历史事实保留 |
| SYNC-01 | 同一窗口执行3次，同文件重复确认 | 一份事实，金额不翻倍 |
| SYNC-02 | 同更新时间记录多于一页/触发分页上限 | 全页或切窗，不丢数据，不误推进游标 |
| SYNC-03 | 第3页失败、已提交页后崩溃、租约过期 | 检查点恢复可重读，旧Worker无权写进度 |
| SYNC-04 | A店限流/失效，B店正常 | A单店延迟/暂停，B继续，父任务标部分 |
| DATA-01 | 售后先到、部分退款、多退款事件/累计变化 | 后补关联，成功退款只计真实事实 |
| DATA-02 | 无paid_at、无退款事件时间、隐藏金额 | 可用部分与缺口分别显示，不伪造零或时间 |
| DATA-03 | 商品全量巡检中断、官方旧版本晚到、导入旧文件 | 不误删商品、不覆盖新状态，冲突可追溯 |
| METRIC-01 | 06文档跨期示例与三行尾差例 | 数额按分精确，两种退款口径不同且标签正确 |
| METRIC-02 | 重算期间发生新退款、更正日期 | 新脏revision不丢失，旧/新日期都重算 |
| MAP-01 | 同ERP SKU跨店、未映射商品、映射改版 | 聚合正确，总店金额不因未映射丢失，版本可追溯 |
| PUB-01 | 草稿编辑后旧预检/元数据过期 | 阻止提交，保留输入，重新校验 |
| PUB-02 | 双击提交、换requestKey重复建默认链接 | 同任务或冲突，无双重远端创建 |
| PUB-03 | 平台已创建但客户端超时/进程崩溃 | unknown→核实→绑定，不自动重发 |
| PUB-04 | 审核拒绝、审核中、受理但未上架 | 分开显示提交与平台状态，不冒称已上架 |
| PUB-05 | 多店预检有错、多店执行有失败 | 预检失败零提交；执行失败仅影响对应店 |
| PUB-06 | 仅支持人工发布或缺少真实链接 | 资料包明确人工路径，链接不凭空拼接 |
| SAFE-01 | 两店发布同SKU数量、ERP期间有线下销售 | 展示人工分配及库存非预占边界，不宣称防超卖 |
| OPS-01 | 密钥轮换、数据库恢复、服务重启 | 事实保留，可解密合法token，unknown仍须核实 |
| SEC-01 | 日志/导出/诊断文件/回调地址 | 无完整token/secret/code和不必要个人信息 |
| SEC-02 | 模板炸弹/宏/公式、恶意图片URL | 限制文件与来源，服务端素材获取不访问内网 |

素材服务对用户URL需要域名/协议白名单及防SSRF；优先使用既有文件模块的受控文件ID。远程图片上传只按官方允许的素材流程处理。

## 6. 性能目标（内部设计目标，需压测）

首版以10家店、近90天累计100万订单明细作为容量评估样本，不代表已支持或已完成压测。任务吞吐受官方限流决定，不承诺实时完成。

本地分页查询 P95 目标≤2秒，预聚合总览 P95≤3秒，创建异步任务≤1秒（不包含网络回调）。测试记录服务器配置、数据库量、并发和冷/热缓存；不足时先优化索引、分批查询和汇总，避免同步Worker拖慢交互请求。

## 7. 运维、灰度与回退

1. 完成数据库备份/恢复和凭据密钥恢复验证。
2. 追加迁移，ERP_PDD_ENABLED=false、ERP_PDD_WRITES_ENABLED=false 部署。
3. 一家店只读小窗口、随后两家最近7天，对账无无法解释的差异。
4. 开周期同步，观察授权失效、限流、积压、成功窗口延迟、缺失金额、unknown发布数量。
5. 开草稿和资料包；发布能力已获批且真实试单验证后，再由运营开启写入，并逐店扩容。
6. 首次真实发布由运营确认店铺、内容及实际副作用；开发阶段不能把替身成功当成真实验收。
7. 异常时先关闭远程写入、暂停新任务；保留队列、检查点、发布attempt和unknown证据。网络发出的请求不能用本地回滚撤销。
8. 需要回退应用时确认旧版本兼容结构，保留新增表。未发送任务可取消，已发送任务仍需核实；不在回退时自动删除远端商品或清空数据库。

建议监控：逐店授权到期、最近完整同步间隔、各窗口失败数、重试/429、租约回收数、队列积压、重算积压、发布unknown停留时间、对账差异。阈值按首周实测设置，告警在ERP任务中心呈现；外部消息通知为后续独立范围。

## 8. 每阶段交付证据

提交代码与迁移、更新接口/字段映射文档、测试摘要、浏览器操作记录、脱敏官方响应样例、业务对账报告、发布核实证据和已知限制。阶段状态区分「框架完成」「替身验证」「官方实测」「业务验收」，不能统一写“已完成”。

下一步可先执行 PDD-001/002 和 PDD-003/005 的方案设计；实际开始写实现代码、申请账户或提交真实发布是新的执行任务。

# 拼多多销售统计口径与数据质量

版本：0.1，2026-10-13。关联：[需求](01-requirements.md)、[数据模型](03-data-model.md)。本口径用于经营分析，不等同于到账、利润或财务记账。

## 1. 基础约定

报表默认人民币、Asia/Shanghai 业务日期。查询起止日期按半开区间 [首日00:00, 末日次日00:00) 转成 UTC。前端明确展示日期范围、所选店铺、时间口径、数据截止时间、完整性和 metricVersion。

支付金额定义为经官方字段核验的买家实际支付金额，拟包含买家实际支付的运费；商品实付和运费分别保存。平台补贴、商家承担优惠、服务费和结算款不能未经核验混入。实际接口只提供商家收入而无买家实付时，字段改称对应来源名称，该店的买家实付指标不可用；不混合不同含义跨店求和。

所有指标使用规范后的唯一业务事实，而不是 API 拉取次数或导入行数。未支付、取消但从未支付订单不计入支付额；已支付后退款订单仍保留原支付额，并单列退款。

金额未知为 NULL；零金额只有在来源明确为 0 时才记为 0。非人民币单列不可合计，第一版不做汇率转换。

## 2. 第一版指标字典

| 页面名称 | 计算方式 | 时间维度及限制 |
| --- | --- | --- |
| 支付订单数 | 已发生有效支付、paid_at 落区间的唯一订单数 | 支付日；同店同单计一次 |
| 支付金额 | 对上述订单的 buyer_paid_amount 求和 | 支付日；包含运费与否须统一核验 |
| 商品实付金额 | 有明确拆分口径的 goods_paid_amount 求和 | 支付日；缺失则不可用 |
| 支付件数 | 对支付订单中已核验数量求和 | 支付日；缺明细显示部分 |
| 客单价 | 已知实付订单的支付额 / 对应已知金额订单数 | 不能用全订单数稀释缺失金额；显示已知覆盖率 |
| 成功退款单数 | 区间内退款成功且可确定成功时间的唯一售后单数 | 退款成功日；多退款事件的售后单只计一次 |
| 成功退款金额（当期发生） | 成功退款事件金额求和，成功时刻落区间 | 退款日；不能使用申请退款金额 |
| 净支付额（当期发生） | 区间支付额 - 区间成功退款额 | 两组不同订单，跨期退款可导致负值；不是结算到账 |
| 支付批次累计退款额 | 区间已支付订单截至 dataAsOf 的成功退款累计 | 以订单支付日归属；跨期退款回写原支付日 |
| 支付批次退款金额占比 | 支付批次累计退款额 / 同批支付额 | 只在两项覆盖和语义一致、分母>0时计算；不是售后申请率 |
| 支付批次累计净额 | 同批支付额 - 截止日同批成功退款 | 随后续退款变化；不表示已收回货款 |
| 商品/SKU支付排名 | 经核验的行实付或明确分摊后的行实付求和 | 支付日；明确排名维度及未映射金额 |
| 平台在售商品数 | 最近完整巡检中确认在售的唯一商品数 | 当前快照；不作为日销量或历史在售数 |

退款件数、退款后净销量只有平台可明确提供明细/数量并已核验时再开放。首版不以退款金额除以单价猜测退款件数。

## 3. 两种退款报表不能混用

看板默认展示「当期发生」：期间发生的支付、期间发生的成功退款、净支付额。提供「按支付订单批次」切换：期间支付订单及其截至数据截止日的累计退款。

展示标签必须分别为「当期退款」「支付批次累计退款」，导出附相同口径。不能把十月支付额减去十一月退款后仍标为「十月当期退款」。

若只有售后累计退款金额没有退款事件时间：
- 能关联订单并核实金额时，可以计入支付批次累计退款。
- 不能计入当期发生退款，不按拉取时间或更新时间冒充退款成功时间。
- 默认看板当期退款和净支付额显示部分/不可用，并列出缺少事件时间的退款金额。
- 后续接口补齐事件时间后，重新计算相应退款日；保留前次报告版本和差异。

## 4. 可核对的跨期示例

以下为虚构验收数据，日期按北京时间：

| 店铺 | 订单 | 支付日期 | 实付 | 售后 | 退款成功日期 | 成功退款 |
| --- | --- | --- | --- | --- | --- | --- |
| A | O1 | 10月1日 | 100.00 | R1 | 10月2日 | 20.00 |
| A | O2 | 10月2日 | 200.00 | R2 | 10月3日 | 50.00 |
| B | O1 | 10月2日 | 80.00 | 无 | 无 | 0.00 |

B 的 O1 与 A 的 O1 是不同业务键。

- 10月1日至2日当期：支付订单3单，支付380.00，退款20.00，净支付360.00。
- 同一支付批次，截至10月2日：累计退款20.00、累计净额360.00。
- 同一支付批次，截至10月3日：累计退款70.00、累计净额310.00。
- 10月3日当期：支付0.00、退款50.00、净支付-50.00，正常显示负数。
- R2 重复拉取或导入两次，只计一次50.00；申请金额与成功金额不能相加。

如果 A/O2 的 paid_at 未提供，即使订单状态显示已支付，也进入待补数据，不猜支付日；对应时段完整性为部分。

## 5. 商品明细分摊与 SKU 映射

优先使用官方明确语义的行实付。若只提供订单商品实付总额但每行优惠前金额可信：

1. 运费单独保留，不随意算入 SKU 商品销售额。
2. 按各行可信的优惠前金额权重分摊订单商品实付。
3. 金额按分计算，用最大余数法分配尾差，同余数按稳定明细键排序，保证各行合计等于订单商品实付。
4. 记录 allocation_method=weighted_estimate，UI/导出标为「分摊估算」。
5. 权重全为零、缺失或不可信时不分摊，列为未分配商品金额，不以数量自动替代。
6. 只有订单总实付且无法分离运费时，商品排名金额不可用；店铺已知支付总额仍可展示。

示例：商品实付100.00、3行等权，稳定键 A/B/C 获33.34/33.33/33.33。所有分页/重跑结果一致。

退款无法关联到商品明细时只纳入店铺订单级退款，列为「未分配退款」；不任意摊到一个 SKU。退款分摊不进入首版 SKU 净额排名。

商品排名提供「平台商品/SKU」和「ERP 商品/SKU」两种视图。未映射商品仍计入店铺支付总额，单列未映射数量及金额。ERP 视图按当前有效映射，返回 mappingVersion；同一 SKU 跨店聚合，规格名称相同不自动认为同一 SKU。

## 6. 数据质量状态

| 状态 | 条件 | 展示 |
| --- | --- | --- |
| complete | 所选店、范围、数据集窗口均完成，关键字段与语义齐全，已处理到选定事实版本 | 可用指标，仍标来源延迟与截止时间 |
| partial | 存失败窗口、授权缺口、未知金额/时间、不可拆退款或未完成重算 | 已知部分金额 + 缺口数/缺口金额，不伪造完整总额 |
| pending_verification | 订单/退款金额语义、状态或版本冲突尚未核对 | 单列待核验，不进入正式指标 |
| unavailable | 核心能力缺失或无法计算该指标 | 显示「不可用」及具体原因 |

complete 表示本系统已知范围完整，不承诺平台绝对实时。退款具备事件时间不代表订单支付范围完整，各指标返回独立质量信息。查询全店汇总不得忽略失败店铺后标记完整。

报告 quality 至少含 selectedShopCount、coveredShopCount、coverageWindows、missingAmountOrderCount、missingPaidTimeCount、refundTimeUnknownAmount、unmappedGoodsAmount、lastCompleteSyncAt、sourceAsOf、computedAt、recomputePending。覆盖率的分子/分母有明确单位，不把金额覆盖率和店铺覆盖率混称「同步率」。

## 7. 重算与一致性

远端事实变更 → 同事务标记受影响日期 → 后台重新聚合 → 校验与替换整天汇总。退款日期或金额被纠正时同时标脏旧日期、新日期及关联订单支付日。

dirty_revision 每次变更递增；Worker 只标记领取 revision 已处理，执行期间新变更保留为待重算。不能用一次 DELETE 清空所有脏日期。

数据规模初期可在一致性数据库快照内查询事实，确保趋势、卡片和排名一致。采用日汇总后报告在同一数据库快照读取，并校验所选范围 processed_revision 与事实变化；未追平时返回 recomputePending/partial，不把新退款事实与旧支付批次指标拼成完整报告。

报表响应包含 metricVersion、mappingVersion（涉及ERP排名时）、dataRevision、dataAsOf。导出任务在创建时冻结允许店集合、筛选、口径和数据截止点；生成时使用一致性快照，审计所用版本。排队期间数据变化必须记录实际生成的 dataAsOf，不宣称生成时数据与点击时金额完全相同。

## 8. 对账与留存

试运行至少两家店，各取最近完整7天，按相同支付时间/退款成功时间、状态、运费及订单范围与官方导出核对。记录订单数、支付额、退款额、差异单号和原因，确认原因后才能验收。

金额要求：经同口径核验的记录精确到分；差额非零必须能定位到具体订单/退款，不以一个总体容差掩盖重复或漏单。平台出数延迟、结算口径与订单口径差别单独记录。

导入不能推进 API 完整游标；可作为补充已覆盖区间的证据，标 source=file。来源混合时报告明确列出且保留冲突。数据质量管理不提供直接改订单金额来“对齐”报表的按钮，修复通过重新同步、核验文件或经审计的来源规则。

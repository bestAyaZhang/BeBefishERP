# 电商内部 ERP 开发规范

## 1. 通用原则

- 代码优先保证清晰、稳定、可追溯。
- 不为第一版未实现的复杂能力提前写大量抽象。
- 库存、财务、单据状态是核心风险点，必须集中处理。
- 所有接口、表字段、枚举值保持命名一致。
- 所有金额和数量计算必须避免浮点误差。

## 2. 后端 Java 规范

### 2.1 命名

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| Controller | 资源名 + Controller | SalesOrderController |
| Service 接口 | 资源名 + Service | InventoryService |
| Service 实现 | 资源名 + ServiceImpl | InventoryServiceImpl |
| Entity | 数据库表对应领域名 | SalesOrder |
| DTO | 场景 + Request/Response | CreateSalesOrderRequest |
| Enum | 领域名 + Enum | DocumentStatusEnum |

### 2.2 事务

- 只有 Service 层开启事务。
- 单据确认、作废、库存变动、财务生成必须使用事务。
- 同一个业务操作不要拆成多个互不相关的事务。
- 查询接口不加事务，除非需要一致性读。

### 2.3 参数校验

- Controller 入参使用 Bean Validation。
- 后端必须校验权限、状态、库存、金额、数量。
- 前端校验只作为体验优化，不能替代后端校验。
- 数量必须大于 0，单价和金额不能为负数，费用金额必须大于 0。

### 2.4 异常处理

- 业务异常使用统一业务异常类。
- 不在 Controller 中捕获并吞掉异常。
- 对用户展示清晰中文错误信息。
- 日志中记录异常堆栈、用户 ID、请求路径、业务单号。

### 2.5 金额和数量

- Java 使用 `BigDecimal`。
- 数据库使用 `decimal`。
- 禁止使用 `double` 和 `float` 处理金额。
- 金额默认保留 2 位小数，成本和数量允许 4 位小数。
- BigDecimal 比较使用 `compareTo`，不要使用 `equals`。

### 2.6 日志

必须记录：

- 登录成功和失败。
- 单据确认和作废。
- 库存变动。
- 收付款。
- 导入和导出。
- 系统异常。

禁止记录：

- 明文密码。
- 完整令牌。
- 短信验证码。
- 不必要的个人敏感信息。

### 2.7 登录与认证安全

- 登录主标识为手机号。
- 密码必须使用强哈希算法保存，禁止明文或可逆加密。
- 短信验证码只存 Redis，不写入业务数据库。
- 短信验证码有效期为 5 分钟。
- 同一手机号 60 秒内不可重复发送验证码。
- 验证码校验成功后必须立即失效。
- 登录失败次数过多时短时间锁定账号或手机号。
- 访问令牌必须设置过期时间，退出登录后当前令牌失效。
- 禁用用户或禁用员工不能登录。
- 飞书登录字段第一版只预留，不展示飞书登录入口，不调用飞书 OAuth。

## 3. 前端 Vue、TypeScript、Tailwind CSS 规范

### 3.1 页面结构

后台页面采用统一结构：

- 顶部筛选区。
- 操作按钮区。
- 数据表格。
- 分页。
- 新增/编辑弹窗或抽屉。
- 详情页或详情抽屉。

样式规则：

- 使用 Tailwind CSS 作为主要样式方案。
- 通用布局、按钮、表单项、状态标签、弹窗、表格工具栏应封装组件。
- 页面内可以使用 Tailwind 原子类，但重复出现 3 次以上的组合应提取为组件或样式封装。
- 不在业务页面写大段自定义 CSS。
- 颜色、间距、字号、阴影等基础设计值应通过 Tailwind 配置统一管理。
- 后台系统以清晰、紧凑、可扫描为主，不做营销页式的大面积装饰。

### 3.2 API 调用

- 所有接口统一放在 `src/api/`。
- 页面不直接拼接后端 URL。
- 请求和响应类型使用 TypeScript interface。
- 统一处理登录过期、无权限、服务器异常。

### 3.3 权限控制

- 路由守卫检查登录状态。
- 菜单根据后端返回权限生成。
- 按钮根据权限编码显示或隐藏。
- 前端隐藏按钮不能替代后端接口权限校验。

### 3.4 表单交互

- 必填项明确标识。
- 保存前进行基础校验。
- 确认、作废、删除等高风险操作必须二次确认。
- 库存不足、导入失败、权限不足必须展示明确原因。

## 4. 数据库规范

### 4.1 命名

- 表名使用小写下划线：`sales_order`。
- 字段名使用小写下划线：`created_at`。
- 主键统一为 `id`。
- 外键字段使用 `{entity}_id`：`customer_id`。
- 唯一索引以 `uk_` 开头，普通索引以 `idx_` 开头。

### 4.2 字段规范

- 编码字段长度默认 `varchar(50)`。
- 名称字段长度默认 `varchar(100)`。
- 备注字段默认 `varchar(500)`。
- 状态字段使用 `varchar(20)`，枚举值由后端统一维护。
- 时间字段使用 `datetime`。

### 4.3 数据变更

- 生产环境表结构变更必须通过迁移脚本。
- 不直接删除业务数据，使用 `deleted` 标识逻辑删除。
- 历史单据、库存流水、财务流水不允许物理删除。
- 初始化数据需要脚本化，例如默认仓库、管理员、基础角色。

## 5. API 规范

- 请求路径以 `/api/` 开头。
- 列表接口使用 GET。
- 新增使用 POST。
- 修改使用 PUT。
- 删除使用 DELETE。
- 业务动作使用 POST，例如 `/confirm`、`/void`、`/import`、`/export`。
- 所有接口返回统一响应结构。
- 分页参数统一为 `page` 和 `pageSize`。

## 6. 产品资料字段规范

- `product_code` 是系统内部产品编码，`item_no` 是业务货号，二者不能混用。
- 货号应保持唯一，用于采购沟通、平台资料、包装资料和内部查找。
- 包装尺寸统一按 cm 存储，字段拆分为长、宽、高。
- 包装体积统一按 cm³ 存储，可由长 × 宽 × 高计算，也允许人工修正。
- 净重、毛重统一按 kg 存储。
- 克重统一按 g 存储，用于需要标识克重的商品或材料。
- 装箱数必须为正整数。
- 包装图片只保存文件地址或对象存储 URL，不把图片二进制写入业务表。
- 前端展示尺寸和重量时必须显示单位，避免 cm、mm、kg、g 混用。

## 7. Git 与分支规范

详细多人协作流程见 [Git 多人协作与版本迭代规范](./07-git-collaboration.md)。

建议分支：

- `main`：生产稳定分支。
- `develop`：测试环境分支。
- `feature/*`：功能开发分支。
- `fix/*`：缺陷修复分支。
- `release/*`：阶段发版分支。
- `hotfix/*`：生产紧急修复分支。

提交信息示例：

```text
feat: add sales order confirmation
fix: prevent negative inventory on assembly
docs: add database design
refactor: split inventory service
test: add purchase confirmation tests
```

每次提交应聚焦一个明确变更，不把无关格式化和业务修改混在一起。

多人开发时，业务代码不直接推送到 `main` 或 `develop`，必须通过 Pull Request 或 Merge Request 合并。

## 8. 测试规范

后端测试优先覆盖业务规则：

- 成本计算。
- SKU 包装资料保存、查询和单位展示。
- 库存扣减。
- 库存不足。
- 应收应付生成。
- 单据状态限制。
- 导入校验。

前端测试优先覆盖关键流程：

- 登录和权限菜单。
- 产品、SKU、物料维护。
- 采购、组装、销售确认。
- 导入失败提示。
- 看板刷新。

任何涉及库存和财务的修改，必须补充或更新测试用例。

## 9. 文档维护规范

- 需求变化先更新需求文档，再进入开发。
- 数据库表结构变化必须同步更新数据库设计文档。
- 新增接口必须同步接口说明或 OpenAPI。
- 开发规范变更需要团队确认后执行。
- 文档文件使用 Markdown，统一放在 `docs/` 目录。

# 产品资料与销售开单设计说明

## 1. 文档状态

- 状态：已于 2026-07-10 经用户批准，可进入实施计划。
- 范围：产品资料、分类、客户、供应商、仓库、库存基础、销售开单、收款记录、欠款应收和销售单打印。
- 技术栈：Java 21、Spring Boot 3.3.5、MySQL 8、Vue 3、TypeScript、Tailwind CSS。
- 开发方式：纵向分批交付，前端支持 Mock/真实 API 切换，所有业务功能严格测试先行。
- Git 规则：开发完成后先由用户验收，只有用户明确要求时才提交 Git。

## 2. 目标与边界

本轮目标是把现有静态产品原型升级为可保存、可查询、可销售的真实业务模块，并跑通以下闭环：

1. 维护分类、客户、供应商和仓库。
2. 创建单规格或多规格产品，维护 SKU、包装资料、图片和供应商采购报价。
3. 通过库存调整建立各仓库 SKU 初始库存，并保留库存流水。
4. 创建销售草稿，选择客户、仓库和 SKU，计算价格、折扣、运费和收款金额。
5. 确认销售单后扣减库存，生成库存流水、收款记录或欠款应收。
6. 对欠款进行一次或多次收款，直到应收结清。
7. 使用选定的现代清晰版 A4 模板打印销售送货单或另存为 PDF。

本轮不包含采购单、采购入库、BOM、组装入库、平台订单导入、完整会计总账、发票开具接口和物流平台接口。这些模块后续复用本轮的产品、供应商、仓库、库存和财务基础能力。

## 4. 分批交付方案

### 4.1 第一批：基础资料与产品

- 分类、客户、供应商、仓库的列表、新增、编辑、启停和查询。
- 产品列表、详情、新增、编辑和启停。
- 单规格产品自动创建默认 SKU。
- 多规格产品按颜色、花纹、容量、尺寸、型号等规格生成 SKU 组合。
- SKU 包装资料、图片和多供应商采购报价。
- 前端 Mock Service 与真实 REST API 使用同一套 TypeScript 类型。

### 4.2 第二批：库存基础

- 多仓库存余额。
- 库存初始化和库存调整。
- 库存流水查询和来源追溯。
- 并发库存扣减所需的数据库锁和事务能力。

### 4.3 第三批：销售草稿

- 销售开单页面和销售单列表。
- 客户、仓库、经办员工、销售日期和 SKU 选择。
- 数量、手工改价、折扣、运费、收款和欠款金额计算。
- 运输方式、结算周期、包装说明、开票状态和物流信息。
- 草稿保存、编辑、详情和删除。

### 4.4 第四批：销售确认与财务

- 销售确认扣库存并写库存流水。
- 保存销售时的产品、规格、售价和标准成本快照。
- 生成应收、初始收款记录和欠款余额。
- 后续多次收款和自动结清。
- 已确认单据作废时生成库存和财务反向记录。
- 现代清晰版 A4 打印和浏览器另存为 PDF。

## 5. 技术架构

### 5.1 后端模块

后端继续采用 Spring Boot 模块化单体，按业务能力分包：

- `masterdata`：分类、客户、供应商、仓库。
- `product`：产品、SKU、规格组合、供应商报价和标准成本。
- `inventory`：库存余额、库存调整和库存流水。
- `sales`：销售草稿、确认、作废和打印数据。
- `finance`：应收、收款和财务冲回。
- `file`：文件元数据、图片上传和存储适配器。
- `auth`：沿用现有登录能力，并为业务 API 增加令牌认证和权限校验。

每个模块按 `api`、`application`、`domain`、`infrastructure` 划分。跨模块只通过应用服务或明确接口调用，不直接修改其他模块的数据表。

### 5.2 持久化

- 业务数据库使用 MySQL 8。
- 使用 Spring Data JPA 处理基础持久化。
- 使用 Flyway 管理数据库版本，禁止依赖 JPA 自动修改生产表结构。
- 金额使用 Java `BigDecimal` 和 MySQL `decimal`。
- 时间统一由后端写入，数据库保存 `datetime(3)`。
- 业务表保留创建人、创建时间、修改人和修改时间。

### 5.3 前端结构

- 引入 Vue Router，每个一级菜单对应独立路由页面。
- 将当前 `WorkspacePrototype.vue` 中的产品、导航和工作台拆为独立页面与组件。
- 页面只通过 TypeScript Service 获取和修改数据。
- Service 提供 `mock` 和 `real` 两种适配器，并由 `VITE_DATA_SOURCE=mock|real` 切换。
- Mock 数据只用于开发和自动化测试，生产构建禁止启用 Mock。
- 已完成模块默认使用真实 API，验收必须连接真实后端和 MySQL。

## 6. 基础资料设计

### 6.1 分类

第一版只开放一级分类，例如玻璃杯、啤酒杯、酒杯、烟灰缸和醒酒器。

字段：

- 分类编码，必填且唯一。
- 分类名称，必填且唯一。
- 排序号。
- 启用状态。
- 备注。
- `parent_id` 和 `level` 作为二级、三级分类扩展字段，第一版统一为空和 `1`。

一个产品第一版只归属一个分类。已经被产品使用的分类不允许物理删除，只能停用；停用分类不能用于新产品。

### 6.2 客户

字段：

- 客户编号，必填且唯一。
- 客户名称，必填。
- 联系人、手机号和联系电话。
- 省、市、区和详细地址。
- 默认运输方式。
- 默认结算周期。
- 备注和启用状态。

系统预置不可删除的“散客”客户。普通零售开单可直接选择散客；停用客户不能用于新销售单。

### 6.3 供应商

字段：

- 供应商编号，必填且唯一。
- 供应商名称，必填。
- 联系人、手机号和联系电话。
- 地址、备注和启用状态。

供应商采购价不直接保存在供应商表或产品表，而是保存在 SKU 与供应商报价关联表中。

### 6.4 仓库

字段：

- 仓库编号，必填且唯一。
- 仓库名称，必填且唯一。
- 仓库地址。
- 是否默认仓库。
- 启用状态和备注。

系统支持多个仓库，但同一时间只能有一个启用的默认仓库。销售开单默认带出默认仓库，也允许用户切换。存在库存或历史单据的仓库不允许物理删除。

## 7. 产品与 SKU 设计

### 7.1 产品主档

产品主档保存多个 SKU 共享的信息：

- 产品编码，必填且全局唯一。
- 货号，必填且全局唯一。
- 产品名称，必填。
- 分类、品牌、产品类型。
- 产品主图、备注和启用状态。

产品类型：

- `simple`：单规格产品。
- `variant`：多规格产品。

### 7.2 单规格产品

单规格产品在保存产品时自动生成一个默认 SKU。界面不要求用户额外进入子 SKU 页面，但售价、成本、条码、库存和包装资料仍然保存在默认 SKU 上。

默认 SKU 编码可由系统按产品编码生成，也允许用户保存前手工填写。后端始终以 SKU 作为销售和库存对象，不建立产品级库存。

### 7.3 多规格产品

多规格产品可维护颜色、花纹、容量、尺寸、型号等可扩展规格项。每个规格项包含多个规格值，系统生成规格值的笛卡尔组合，例如：

- 颜色：透明、烟灰。
- 花纹：竖纹、樱花纹。
- 组合 SKU：透明 + 竖纹、透明 + 樱花纹、烟灰 + 竖纹、烟灰 + 樱花纹。

用户可以删除实际不存在的组合。SKU 生成后，删除规格值前必须检查该 SKU 是否已有库存或历史单据；存在历史业务数据时只能停用 SKU。

### 7.4 SKU 字段

- SKU 编码，必填且全局唯一。
- 条码，可为空；填写时全局唯一。
- SKU 名称和规格显示文本。
- 销售单位，例如只、套、箱。
- 默认售价。
- 标准成本。
- 包装长、宽、高，单位 cm。
- 包装体积，单位 cm³，默认按长 × 宽 × 高计算并允许人工修正。
- 净重和毛重，单位 kg。
- 克重，单位 g。
- 包装方式和装箱数。
- SKU 图片、包装图片和外箱图片。
- 启用状态。

数量、价格、尺寸和重量不得为负数；装箱数必须为正整数；毛重不得小于净重。

### 7.5 多供应商采购报价

同一个 SKU 可以关联多个供应商，每个报价包含：

- 供应商 ID。
- 供应商货号。
- 采购价。
- 最小采购量。
- 是否默认供应商。
- 启用状态和最后更新时间。

同一 SKU 与同一供应商只能存在一条启用报价，同一 SKU 同时只能有一个默认供应商。多规格产品支持批量把同一供应商报价应用到全部 SKU，也允许单独覆盖某个 SKU 的采购价。

SKU 标准成本默认取默认供应商采购价。切换默认供应商或修改默认供应商采购价时，界面必须询问是否同步更新标准成本，不静默覆盖。销售单确认时保存标准成本快照，后续采购价或标准成本变化不影响历史毛利。

### 7.6 图片

- 支持直接上传产品主图、SKU 图片、包装图片和外箱图片。
- 开发环境保存到本机 `uploads/` 目录，数据库只保存文件元数据和访问 URL。
- 文件名使用系统生成的唯一名称，不使用用户原始文件名作为存储名。
- 第一版允许 JPG、JPEG、PNG 和 WebP，单文件最大 10 MB。
- 存储能力通过接口封装，后续可切换阿里云 OSS 等对象存储。

## 8. 库存设计

### 8.1 库存余额

库存余额以 `warehouse_id + sku_id` 唯一，字段包含当前数量和版本号。第一版默认不允许负库存。

### 8.2 库存调整

库存初始化和日常盘盈盘亏统一使用库存调整单，不允许用户直接编辑库存余额。库存调整单采用草稿、已确认、已作废状态。

- 草稿不影响库存。
- 确认后更新库存余额并写库存流水。
- 作废已确认调整单时写反向库存流水。

### 8.3 库存流水

每次库存变化必须记录：

- 仓库、SKU、方向和数量。
- 变动前数量和变动后数量。
- 来源类型、来源单据 ID 和来源单号。
- 操作人和发生时间。

库存余额用于快速查询，库存流水用于审计和追溯，两者必须在同一数据库事务内更新。

## 9. 销售开单设计

### 9.1 销售单主信息

- 销售单号，格式为 `SO + yyyyMMdd + 4 位当日流水`，例如 `SO202607100001`。
- 客户、仓库、销售日期和经办员工。
- 运输方式、结算周期和收款状态。
- 送货地址、物流公司和运单号。
- 包装说明、是否需要开票、开票状态和备注。
- 商品金额、折扣金额、运费、应收合计、已收金额和欠款金额。
- 单据状态、确认人、确认时间、作废人和作废时间。

运输方式：

- `pickup`：自提，不要求物流信息。
- `delivery`：送货上门，默认带出客户地址。
- `freight`：托运，可填写物流公司和运单号。
- `express`：快递，可填写物流公司和运单号。

结算周期：

- `daily`：日结。
- `monthly`：月结。
- `quarterly`：季度结。
- `yearly`：年结。

结算周期与实际收款渠道分开保存。实际收款渠道包括现金、微信、支付宝、银行转账和其他。

### 9.2 销售明细

用户可按货号、产品名称、SKU 编码和条码搜索启用 SKU。明细展示当前仓库可用库存，字段包含：

- SKU ID、产品和规格快照。
- SKU 编码、货号和销售单位快照。
- 数量、原始默认售价、实际销售单价和折扣率。
- 明细金额、标准成本和成本金额。
- 明细备注。

明细金额由后端按 `数量 × 实际销售单价 × (1 - 折扣率 / 100)` 计算并四舍五入到 2 位。应收合计为所有明细金额之和加订单运费。前端计算只用于即时预览，保存和确认时以后端结果为准。

### 9.3 状态流

- `draft`：草稿，可编辑和删除，不影响库存和财务。
- `confirmed`：已确认，不能直接修改，允许查看、打印和按权限作废。
- `voided`：已作废，不参与有效销售、库存和应收统计。

销售确认必须：

1. 校验单据仍为草稿，防止重复确认。
2. 校验客户、仓库和所有 SKU 处于启用状态。
3. 校验数量大于 0、价格不小于 0、折扣率在 0 至 100 之间。
4. 校验已收金额不小于 0 且不大于应收合计。
5. 按固定顺序锁定涉及的库存余额记录，检查库存充足。
6. 扣减库存并写库存流水。
7. 保存销售和成本快照。
8. 生成应收记录；有已收金额时生成初始收款记录。
9. 更新销售单为已确认。

以上步骤在同一个数据库事务内完成，任何一步失败全部回滚。

### 9.4 作废

已确认销售单不允许删除。作废时：

- 增加原销售数量并生成反向库存流水。
- 将原应收标记为已作废。
- 对有效收款生成金额相反的冲回记录，并保留原记录。
- 将销售单更新为已作废，记录作废人、时间和原因。

作废操作必须有单独权限并要求二次确认。已作废单据仍可查看和打印，打印时显示“已作废”标识。

## 10. 收款与欠款应收

### 10.1 应收

每张已确认销售单生成一条应收记录，即使销售单已经全额收款也保留该记录。状态包括：

- `unpaid`：未付款。
- `partial`：部分付款。
- `paid`：已结清。
- `voided`：来源销售单已作废。

欠款金额始终由应收金额减去有效收款金额计算，不单独允许手工修改。

### 10.2 收款记录

每次收款生成独立记录，包含：

- 收款单号、客户、来源应收和来源销售单。
- 收款金额、收款渠道和收款日期。
- 经办员工、备注和记录类型。

一条应收可以分多次收款。每次收款后重新计算累计已收和欠款金额，累计收完后应收自动变为已结清。收款总额不得超过欠款金额。

冲回不删除原收款记录，而是创建关联原记录的反向记录。

## 11. 打印设计

默认采用用户选择的 B“现代清晰版”，纸张为 A4 纵向。打印页面独立于系统菜单和操作栏，并提供浏览器打印和另存为 PDF。

打印内容：

- 公司名称、单据标题、销售单号和日期。
- 客户名称、收货人、电话和送货地址。
- 仓库、经办人和计划发货日期。
- 运输方式、结算周期、收款状态和开票状态。
- 货号、SKU 编码、商品名称、规格、数量、单位、单价和金额。
- 商品金额、运费、应收合计、本次已收、尚欠金额和金额大写。
- 包装与交付说明、备注。
- 库管员、业务代表和客户签字/日期栏。

明细行随数据自动增减，不打印无数据的固定空白行。明细超过一页时重复表头，并在最后一页显示金额汇总和签字区。已作废单据增加醒目的“已作废”水印，但不改变原始金额和商品快照。

## 12. 核心数据库表

### 12.1 基础资料

- `product_category`：分类及未来层级字段。
- `customer`：客户和默认运输/结算信息。
- `supplier`：供应商资料。
- `warehouse`：仓库和默认仓库标识。

### 12.2 产品

- `product_spu`：产品主档。
- `product_spec`：产品规格项。
- `product_spec_value`：规格值。
- `product_sku`：可销售和可库存 SKU。
- `product_sku_spec_value`：SKU 与规格值关联。
- `sku_supplier_quote`：SKU 的多供应商采购报价。
- `file_asset`：上传文件元数据。

### 12.3 库存

- `inventory_balance`：仓库 SKU 库存余额，唯一键为 `warehouse_id, sku_id`。
- `inventory_ledger`：不可修改的库存流水。
- `stock_adjustment`：库存调整单主表。
- `stock_adjustment_item`：库存调整明细。

### 12.4 销售与财务

- `sales_order`：销售单主表和物流、结算、金额、状态信息。
- `sales_order_item`：销售明细和商品/价格/成本快照。
- `receivable`：销售应收。
- `receipt_record`：收款及反向冲回记录。

所有历史单据、库存流水、应收和收款记录禁止物理删除。

## 14. 权限与安全

- 所有业务 API 必须登录后访问。
- 前端路由守卫按当前用户权限生成菜单并阻止无权限页面访问。
- 后端必须再次校验权限，不能依赖前端隐藏按钮。
- 权限至少包含查看、新增、编辑、启停、确认、作废、库存调整、收款和打印。
- 图片上传校验实际文件类型、扩展名和文件大小。
- 数据库连接、文件目录和 Mock 开关使用环境配置，不写死在源代码。
- 操作日志记录产品价格/成本修改、库存调整、销售确认/作废和收款/冲回。

## 15. 错误处理

业务错误使用稳定错误码并返回明确中文信息：

- `DUPLICATE_PRODUCT_CODE`：产品编码已存在。
- `DUPLICATE_ITEM_NO`：货号已存在。
- `DUPLICATE_SKU_CODE`：SKU 编码已存在。
- `INVALID_PRODUCT_VARIANT`：规格组合不完整或重复。
- `SUPPLIER_QUOTE_CONFLICT`：同一 SKU 的供应商报价冲突。
- `DEFAULT_WAREHOUSE_CONFLICT`：只能设置一个默认仓库。
- `INVENTORY_NOT_ENOUGH`：指定仓库的 SKU 库存不足。
- `ORDER_STATUS_INVALID`：当前单据状态不允许该操作。
- `ORDER_ALREADY_CONFIRMED`：销售单已确认，请勿重复操作。
- `RECEIPT_EXCEEDS_OUTSTANDING`：收款金额超过剩余欠款。
- `IMAGE_TYPE_NOT_ALLOWED`：图片类型不支持。
- `IMAGE_TOO_LARGE`：图片超过 10 MB。

前端保留用户已输入内容，并把字段错误显示在对应字段附近；事务类错误在页面顶部集中提示，不把数据库异常或堆栈暴露给用户。

## 16. 测试先行与验收场景

每一项生产代码必须先有失败测试，并确认测试因缺少目标行为而失败，再实现最小代码使其通过。

### 16.1 后端

- 单规格产品保存后自动生成一个默认 SKU。
- 多规格产品生成正确组合，并拒绝重复 SKU 编码和重复规格组合。
- 一个 SKU 可维护多个供应商采购价，但只能有一个默认供应商。
- 更新默认供应商采购价时按用户选择决定是否更新标准成本。
- 同一时间只能有一个启用的默认仓库。
- 库存调整确认后余额与流水同时变化，失败时全部回滚。
- 销售确认库存充足时只扣减一次并生成流水。
- 库存不足、SKU 停用或重复确认时不产生任何库存和财务变化。
- 未付款、部分付款和全额付款生成正确应收状态。
- 同一应收支持多次收款，超额收款被拒绝，累计收完后自动结清。
- 作废销售单生成反向库存和财务记录并保留历史。
- 并发确认两张销售单时不能造成负库存。
- 打印数据使用销售快照，产品后续改名或改价不影响历史打印内容。

领域和应用服务使用 JUnit 5 测试；REST 接口使用 MockMvc 测试；事务、锁和数据库约束使用 MySQL 集成测试验证。

### 16.2 前端

- Mock 和真实 Service 满足同一 TypeScript 接口。
- 菜单显示工作台及各独立一级菜单，库存和财务子菜单正确展开。
- 产品表单可切换单规格/多规格并生成、删除规格组合。
- 产品详情正确展示 SKU、包装资料、图片和多供应商报价。
- 销售开单可搜索 SKU、展示仓库库存并正确预览金额。
- 运输方式切换时正确显示地址或物流字段。
- 收款状态和欠款金额随输入变化，但保存结果以后端为准。
- 无权限用户看不到操作入口，直接访问路由也被阻止。
- 打印页不显示菜单和按钮，A4 版式包含全部确认字段。

前端组件和 Service 使用 Vitest 与 Vue Test Utils 测试。每批完成后运行全量前后端测试，并在浏览器中验证桌面和窄屏页面；打印页额外验证 A4 打印预览和分页。

## 17. 完成标准

本轮完成需要同时满足：

1. 四批功能均连接真实后端和 MySQL，可在刷新浏览器后保留数据。
2. Mock 模式可用于前端开发，但生产构建不能启用。
3. 产品、库存、销售、收款和欠款的核心验收场景全部通过。
4. 销售确认、作废和收款不存在库存或财务半成功状态。
5. B 版现代清晰销售送货单可 A4 打印并可另存为 PDF。
6. 所有新增功能均遵守测试先行，并通过全量自动化测试。
7. 用户完成页面和业务验收后，再按用户指令决定是否提交 Git。
